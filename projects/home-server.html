Turning a $60 Raspberry Pi into a Real Piece of Infrastructure

Network-wide ad blocking, intrusion detection, full observability, and workflow automation — running on a single low-power board, with no ports exposed to the internet.

Personal infrastructure project Debian 13 · Docker · Raspberry Pi 4
Docker Compose Prometheus Grafana Loki CrowdSec Pi-hole Tailscale n8n Linux hardening

A Raspberry Pi 4 sounds like a toy — four ARM cores, 4GB of RAM, the kind of thing you'd use to blink an LED. Mine currently runs twelve production services around the clock: it blocks ads for every device on my network, watches for intrusion attempts, collects and visualizes metrics and logs from itself and every container it hosts, runs automated workflows, and gives me secure remote access from anywhere — without a single port forwarded on my router.

This post walks through what the setup does, how it's put together, and — more usefully than a features list — what actually went wrong along the way and what I'd do differently next time.

What it actually does

Five real jobs, running on one board:

  • Network-wide ad blocking — Pi-hole sits as the DNS resolver for every device on the network, so ads and trackers get filtered out before they even load, on phones, laptops, and smart TVs alike — no per-device extensions needed.
  • Intrusion detection — CrowdSec watches logs for attack patterns and automatically blocks offending IPs at the firewall, backed by a crowdsourced threat-intelligence feed.
  • Full observability — every container and the host itself report metrics into Prometheus, logs into Loki, and both get visualized in Grafana dashboards, with an uptime/latency prober (blackbox-exporter) checking that the important services are actually reachable.
  • Workflow automation — n8n handles the "if this happens, do that" glue work that would otherwise be a pile of cron scripts, including a daily crucial-alerts digest email (details below).
  • Secure remote access — Tailscale creates a private mesh network back to the Pi, so I can reach dashboards and services from anywhere without opening a single port on the home router — the attack surface from the internet is effectively zero.

Anything with a web UI that doesn't have its own login screen — Grafana, Prometheus, Loki, Portainer, blackbox-exporter — is deliberately bound to 127.0.0.1 only. Pi-hole's DNS and admin UI are the only things intentionally open to the local network, because that's the one service whose entire job requires it. Those loopback ports are then republished over HTTPS to just my Tailscale devices with tailscale serve — same containers, same loopback bind, no LAN exposure, reachable from anywhere on the tailnet at the box's own hostname.

The daily digest workflow

There's no Alertmanager in this stack — Prometheus scrapes and blackbox-exporter probes, but nothing pre-triages a failure into a fired alert. So instead of waiting on alerts that don't exist, an n8n workflow runs once every 24 hours and reads raw state directly from every source that has anything worth knowing:

  • CrowdSec — currently active IP bans.
  • Prometheus — any scrape target reporting up == 0, and any blackbox probe reporting probe_success == 0 (Pi-hole / Grafana unreachable).
  • Loki — an accurate 24h count of error|critical|fatal log lines via count_over_time, deliberately excluding Loki's own routine query-cancellation noise ("context canceled", "EOF") so that churn doesn't drown out real errors — plus a small sample of matching lines for the model to quote from.
  • cAdvisor — which containers (re)started in the last 24h, the one check that catches a crash-and-recover that the instant up == 0 query above would otherwise miss.
  • Node health — disk free, memory available, swap used, and CPU temperature straight from node-exporter.
  • OOM & CrowdSec health — containers killed for memory overuse, and CrowdSec's own internal alert-creation count. This is also where a known, permanent gap gets surfaced honestly rather than hidden: CrowdSec has no Pi-hole/dnsmasq parser installed, so 100% of the ~80k Pi-hole log lines it sees every day fail to parse. That counter is reported as a lifetime total, not a 24h delta — an increase() over a counter with no clean reset window produced a wildly inflated, misleading number the first time this ran.
  • Pi-hole stats — whether ad-blocking is actually enabled (the one Pi-hole failure mode that's a real security concern, since DNS keeps resolving fine and nothing else would flag it), plus today's block count and query volume as context.

Everything gets merged and handed to an LLM (via OpenRouter) with explicit grading rules — active bans, down targets, probe failures, high disk/temp, or ad-blocking disabled all grade CRUCIAL; one-off restarts or elevated error counts grade MEDIUM; a clean day still grades INFO and gets a short factual email rather than silence. The grade lands directly in the subject line, so a quiet day is triageable from the inbox list without opening anything, and a bad day is unmistakable.

Challenges & what I'd do differently

The interesting part of any infrastructure project isn't the list of tools — it's what broke, what was quietly wrong, and what it took to notice.

Challenge

I was running two overlapping monitoring stacks without realizing it

An earlier setup (OpenObserve + Vector) had been layered on top of the existing Prometheus/Grafana/Loki pipeline, duplicating exactly the same metrics and logs through a second path. It was silently eating CPU and memory for zero added value, and the OpenObserve build in use was a pre-release version (v0.14.1-rc1) with far less production track record than the tools it was duplicating.

Lesson

Audit what's actually running before adding more

It's easy to bolt on a new tool to solve a problem an existing tool already solves, especially on a box that accumulates services over time. Removing the duplicate stack dropped load average from 2.97 down to roughly 1.0–1.6 and freed up over half a gigabyte of swap — a bigger performance win than any tuning would have delivered.

Challenge

Several admin dashboards were reachable by anyone on the Wi-Fi

Grafana, Prometheus, Loki, and Portainer were all bound to 0.0.0.0 — reachable by any device on the local network. Prometheus and Loki don't even have a built-in login screen, so that meant metrics, logs, and container controls were sitting open to anyone who joined the Wi-Fi.

Lesson

"It's just the LAN" is not a security boundary

Guest devices, IoT gadgets, and anything else on the same network can reach anything bound to a public interface. I rebound every admin surface to 127.0.0.1 and now reach them exclusively over Tailscale or an SSH tunnel — the services that truly need LAN access (DNS, admin UI) are the only ones left open, and that was a deliberate decision, not a default.

Challenge

One container ignored my port bindings entirely

Pi-hole's exporter runs in Docker's host network mode for DNS reasons, which means Docker's normal port-binding controls simply don't apply to it — it was exposed to the whole LAN no matter what the compose file said.

Lesson

Host-network containers need firewall rules, not port config

I locked it down with iptables rules restricting the port to loopback, Tailscale, and the Docker bridge, then persisted the rule with netfilter-persistent so it survives a reboot. Compose-level settings aren't enough once a container opts out of Docker's network isolation.

Challenge

A metrics exporter was silently broken and nothing said so

Prometheus showed the Pi-hole exporter as scraped fine, but every value was zero — two stacked root causes. The Prometheus container had no extra_hosts entry, so host.docker.internal (needed to reach a host-networked container) didn't resolve at all. Separately, Pi-hole's real admin password had drifted from .env, because that variable only seeds the password on first-ever init, not on every restart.

Lesson

"Up" isn't the same as "correct"

A scrape target can report healthy while every number it returns is garbage. Fixed both: added extra_hosts: host-gateway to Prometheus, reset the password to match .env. Real query and block stats now flow — the same fix pattern (missing extra_hosts) turned up again fixing a blackbox→Pi-hole uptime probe, which also needed a dedicated module sending Host: pi.hole to get past Pi-hole's anti-DNS-rebinding check — and, in the process, a stale single-file config bind mount (Docker keeps referencing the old inode after an in-place edit; only --force-recreate picks up the change) that's worth remembering for any other config mounted the same way on this box.

What's next

Every real infrastructure project has an open list. Mine:

  • Pin container image versions instead of tracking :latest, so a bad upstream release can't surprise me — plus update notifications via Diun.
  • Automated, scheduled backups of Docker volumes, Pi-hole config, and dashboards — right now they only exist on one disk.
  • Turn off the desktop GUI that's still enabled but unused, now that everything is managed headlessly.
  • Confirm SSH is locked to key-only authentication.
  • Put the 400+ free gigabytes of storage to work as a proper NAS (Samba, Syncthing, or Immich are the leading candidates).

Why this matters

None of these tools are exotic — Docker, Prometheus, Grafana, and a firewall are industry standard. What this project actually demonstrates is the less glamorous half of infrastructure work: auditing a running system for redundancy and exposure, tightening a security boundary that looked fine until you checked it, and making a deliberate, documented tradeoff between automation and stability rather than defaulting to "auto-update everything" or "update nothing." That's the same judgment call that shows up in production systems at any scale — just with a much smaller (and quieter) box to prove it on.
