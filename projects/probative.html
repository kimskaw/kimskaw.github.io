Probative: An LLM Triage Pipeline That Doesn't Trust Its Own Model

A local research prototype, not a deployed security tool. It asks one narrow question: when a language model writes up a security alert, can its findings be checked instead of trusted? Detection is the deliberately simple front-end, a set of rules whose recall is low (41.7%), because the work is what happens after a finding is written, where code and a second model try to prove it wrong.

Probative is the evidential standard it holds the model to: a claim counts only if the evidence actually supports it. It runs on captured honeypot traffic (a honeypot is a decoy server attackers probe) and synthetic endpoint telemetry, not a live network.

kim@probative: ~
$ python -m orchestrator.loop ───────────────────────────── detect sigma rules · severity in code model one LLM · 3 read-only tools pass a code re-checks every figure ● pass b a second AI model verifies it ● verdict reported, or handed to a human no daemon · polls and exits · cron $

Everything runs locally on one machine, and no security data ever leaves the host for cloud inference.

In short

  • The problem. An LLM triaging a security alert writes fluent, confident prose whether or not any of it is true.
  • The approach. Structure over prompting: the model only explains what the evidence shows, and code or a second model makes every decision that carries consequences.
  • What holds up. A model-free check catches 13 of 13 hand-crafted fabrications, refuses 89 of 90 fabricated counts, and wrongly rejects 0 of 9 genuine findings. Whether the second, model-based pass earns its cost is still being measured, and the answer may be no. And I found a flaw in my own testing method and rebuilt it.
  • Stated plainly. Just 64 investigated cases so far, and detection recall is 41.7%. Every number here rests on a small operational history, reported rather than rounded, not a production estate.

01 Design

What it does

  • Collects and normalises: endpoint, honeypot, and multi-host logs, all behind one adapter interface (Sysmon via Loki, an isolated SSH honeypot, Wazuh as a multi-host collector). The event store is append-only, so re-reading the same time window changes nothing.
  • Decides what deserves attention: nine SQL projections that expose the raw JSON as queryable columns, and 21 Sigma rules compiled to SQL, each carrying an ATT&CK technique, a severity and a false-positive note. Severity is fixed here, before any model runs. Coverage is deliberately narrow, not a strength to lean on: recall is 41.7%, and the point is not how much these rules catch but what happens to a finding once one fires.
  • Filters noise in a fixed order, and the order is load-bearing: allowlist first, then de-duplication by fingerprint, then known-benign classification. The same fingerprint fifty times makes exactly one case.
  • Investigates with exactly three read-only tools: the case's events, cached reputation data, the rule's own text. No shell, no filesystem, no network, no writes; a test asserts that list holds those three and nothing else.
  • Retrieves precedent, without letting it become evidence: the model can read past cases that already passed verification, found by keyword and by local embedding search with the two rankings fused rather than scored (RAG). It cannot cite them. A claim can only ever cite events from its own case.
  • Verifies in two passes: a deterministic pass first, which is authoritative, then a second AI model, the verifier, that must not be the first one.
  • Records every model call: one append-only row per LLM call, prompt and response verbatim, so any conclusion stays checkable long after the fact. The full audit trail is section 07.

Where the model is, and is not

Only two stages in the whole pipeline are an LLM, and neither can open a case, set a severity, or write to the evidence store.

Pass B is kept deliberately ignorant. It sees the raw events and the single claim being judged, and nothing else: not the investigator's summary, not its reasoning, not how confident it was, not the past cases that were retrieved. Any of those would tempt it to agree instead of check. A high confidence score is a reason to look harder, never a reason to believe.

02 Architecture

The architecture, end to end

The same map as a diagram, from a log line to a recorded verdict. Everything above the two model calls decides what deserves attention; everything below them is a check the model cannot influence.

All inference runs locally: SQLite, Ollama, no message queues, no web framework. Reputation enrichment is the one outbound dependency, and only public indicators leave the host, never event text. Nothing runs as a daemon: every entry point polls and exits with all state in SQLite, so a kill at any moment is safe and cron is the scheduler.

03 Defense

Prompt injection, answered by subtraction

Fabrication is the failure this pipeline is built around. Prompt injection is the other one, and this pipeline invites it: it reads honeypot sessions, so some of the text reaching the model was typed by an attacker, and a Sysmon command line is no safer. The rule is blunt: all telemetry is hostile input, wherever it came from. Getting that rule applied everywhere took two attempts, which is a story further down the page.

The defence is not a cleverer prompt but subtraction. Every piece of event text passes one sanitiser before any model sees it: a denylist of known instruction markers, each replaced with a visible token rather than deleted, because deleting a marker from text an attacker wrote can splice a new one together out of what surrounds it. A denylist against natural language is leaky by nature, and the design does not pretend otherwise. The attacker's prose still reaches the model, because the prose is the evidence; what gets defused is the scaffolding that would let it pose as an instruction. The same sanitiser covers enrichment payloads, the verifier's inputs, and the claim sentence itself.

Measured directly, the denylist catches 7 of 7 literal phrases and 1 of 13 evasions. Leetspeak, a Cyrillic character, a zero-width space, another language, base64, and a phrase split across two commands all reach the model untouched. The denylist is not a defence, and the code has always said so. What actually contains an injection is structural, and that is what the rest of this section is: read-only tools, severity decided before any model runs, and every cited token checked against stored evidence. Six evasion families were run through the full pipeline against matched controls, and severity moved zero times.

The other subtraction is capability. The investigator's three tools were chosen for what they cannot do: an injected instruction can ask for a shell, a file write, an outbound request, or a change to the case, and none of those verbs exist in the toolset, so the most a successful injection can command is another read of evidence the model already has.

What subtraction buys is that injection degrades into hallucination. A prompt that steers the model cannot raise a severity, open a case, or write to the store, because the model never had those powers. The most it can do is make the model write a wrong finding, and a wrong finding faces the same citation checks and the same second model as an honest mistake. The one thing sanitisation cannot prevent is a model talked out of reporting: a case whose investigator produces nothing usable is not closed quietly but handed to a human, which is the fail-safe for every other failure on this page.

04 Evidence

What it caught

The checks are only worth anything if they refuse fabrication that looks real, so every finding is run against them before it can stand. Here is what they caught, verbatim from the fixture, from the blunt to the subtle. Each verdict was written before the check ever ran. 

01_fabricated_event_id
  claim  "An encoded PowerShell command was executed"
  cites  01DOESNOTEXIST00000000000
  caught by Guard 2: cited id resolves to no stored row

12_ip_built_from_present_octets
  claim  "Traffic originated from 20.45.13.18"
  lie    each octet is a number the evidence states; only the whole-token rule can catch it
  caught by Pass A: the full address never occurs as one token

The second one is worth reading twice, because it shows what this check is. Pass A verifies presence, not arithmetic: a figure with no matching token in the cited evidence cannot be real. The naive way to check that looks for the digits anywhere in the text, and a fabricated 12 hides comfortably inside a timestamp reading 2012. Splitting the evidence into whole tokens first catches the invented address, and across a fixture of ninety invented counts it rejects 89, with no new false rejections against the findings actually stored. The one survivor, 33, genuinely appears in the evidence as its own token, which is the honest limit of the check: a figure that happens to occur somewhere in the text gets through, and whether a real number is attached to the right claim is the second model's problem, not this one's.

And one from the wild, not the fixture: a real certutil-download case investigated on 18 August, where Pass A found every cited token present and Pass B still refused it. 

claim   "The parent process was cmd.exe and the acting user was
         DESKTOP\bob on a desktop workstation"
pass A  all claims supported by cited evidence
pass B  FAIL: the logs identify the user as DESKTOP\bob and say
        nothing about the machine type
result  NEEDS_HUMAN

The username implies a desktop; nothing in the evidence states one. That inference-dressed-as-observation is now its own fault class in the boundary set, username_implies_hardware. It is one of the hand-authored fixtures the checkers are scored against, a frozen benchmark that runs in CI with no model and no network. On it the model-free pass catches 13 of 13 hand-crafted fabrications, 13 of 13 by the intended rule rather than by luck, refuses 89 of 90 fabricated counts, and wrongly rejects 0 of 9 genuine findings. Whether the second, model-based pass earns its cost is a separate question, still being measured.

05 The console

The analyst console

All of that produces rows in a SQLite file: 990,247 events, 106 alerts raised from them, 64 cases opened and investigated, 316 claims checked. The console is how a human reads them.

A local console over the same SQLite file: a triage queue, a case view where every claim links to the raw event it cites, a Sigma rule editor that back-tests a rule against history before it can be saved, and the metrics table. Built on stdlib http.server: no web framework, no new dependency, and the orchestrator is untouched.

The bind address is configurable, localhost by default, and the console refuses to start without a password precisely because loopback stops being a boundary the moment a tunnel or a reverse proxy forwards to it. It writes exactly three things: an analyst's verdict, a detection rule that must compile before it saves, and .env. The password carries the weight for all three; the last two are additionally refused on a non-loopback bind, a defence in depth against misconfiguration rather than a boundary in itself. The .env write is the sharpest privilege the console holds, because repointing a model at a hosted endpoint would ship evidence off-host, which is exactly why it sits behind both conditions.

Passwords are PBKDF2-hashed; every state-changing request is Origin-checked, so the cookie path cannot be ridden from another site.

Back-testing exists because a rule matching most of its logsource is a queue flood rather than a detection, and breadth is only judged once there is enough history to judge it. Every number on the metrics page is a query against the database rather than a counter kept while running, so a crash mid-run cannot inflate it.

Storage, models, strictness and providers are editable from the console, written back to .env with its comments preserved. Every field is declared in a validating registry, so it refuses a verifier model equal to the investigator's, a retention window of zero, or any key it does not declare.

06 Failures

Four things that broke

What broke

A schema validates form; only evidence validates truth

Grammar-constrained decoding stopped the investigator from calling its tools, so it answered from nothing: schema-perfect findings about attacks that never happened, on hosts that do not exist, citing invented ids like event-12345. Guard 1, the schema, saw nothing wrong with any of them; Guard 2, which checks every cited id against a real stored row, caught every one.

The three structured-output modes were not interchangeable, and only one of them left the tools reachable at all.

Output modeTool callsResult
ToolOutput (default)yes80% valid, 20% malformed XML
NativeOutputzero0/2 valid, fabricated whole incidents
PromptedOutputzero0/3 valid, same
What broke

Testing the guard is not testing the thing that arms it

The retry cap was tested, but the query that picks up work only looked for freshly enriched cases, so a returned case was stranded and the budget was never spent. A later audit found the same shape in 86 other places: the noise filter's ordering was not merely untested but unobservable, because no fixture ever built a case where two rules disagreed.

What broke

Context decides whether a rule is right, not the rule

The RFC1918 allowlist classified every honeypot alert as internal and benign, so 26 events produced zero cases and nothing reported an error. A honeypot has no legitimate users, so internal traffic arriving there means lateral movement, more alarming than an external scan, not less.

What broke

A rule phrased around one input gets implemented at that input

"Treat all telemetry as hostile" got built into the events tool and stopped there, while the enrichment tool returned Shodan hostnames and banners (both attacker-controlled) straight to the model. The threat is better stated as anything attacker-influenceable that reaches the prompt, including data arriving through a trusted vendor's API.

07 Audit trail

The ledger: every model call, on the record

One SQLite table, one row per call to a language model, written before the pipeline moves on. Each holds the exact prompt sent and the exact response returned, verbatim, not a summary and not a hash: a recent investigator row is a 3,896-character prompt and a 2,237-character response, exactly as they went to the model and came back.

"The model said so" is only checkable if the exact words survive. The ledger is what makes an AI's conclusion auditable months later instead of trusted in the moment.

Why it is a line, not a callback

  • The rule. Every LLM call writes a ledger row; a call with no row is a bug, with no exception for retries, cheap calls or test runs. It is one of the project's nine hard invariants, enforced in code rather than asked for in a prompt.
  • Where the write sits. In the same error-handling block as the call, so the row lands even when the call fails, and on failure it captures what the model actually emitted, which is when it matters most.
  • Why not an agent framework. LangChain and LangGraph own the call loop, so recording becomes a callback you register and hope fires on every path. Here the write is a line you can point at.
What it caught

A column that silently stayed empty

The tool_calls column existed in the schema and nothing ever wrote to it: 256 rows of NULL. Nothing errored, no test failed, reports rendered, metrics computed. It hid that get_rule, one of the investigator's three tools, had never worked, so every finding in that window was written without the detection rule it rested on. The ledger is what eventually made this visible. A missing row is the one thing that would have kept it hidden.

Prompts carry honeypot text, which is attacker-controlled, so past a retention window the prompt and response are replaced with a marker and a SHA-256. The row itself survives on purpose: COUNT(*) still proves no call went unrecorded once the content is gone. Deleting rows would destroy the very count the ledger exists for.

08 Method

Agreement with an incumbent is not accuracy

The verifier has to be a different model from the investigator, and two 17GB models will not both stay loaded on a 24GB card, so every case pays for a model swap. A small verifier would end that, so three challenger models were scored on how often they agreed with the current one. The agreement was low, coin-toss low, and the conclusion wrote itself: closer to chance than to competence, so small models cannot verify.

That conclusion was wrong, because agreement measures sameness rather than correctness. It treats the incumbent as right by definition, so every disagreement counts against the challenger. Two experienced radiologists reading the same ambiguous scan disagree often enough that the disagreement is a studied quantity in its own right, and scoring one against the other would tell you the cases were hard, not that either doctor was bad.

Agreement tells you two models are the same. Whether either is right is a different question, and it needs an answer key written before either one runs.

So the question was asked again with the answer key written first: fabrications a verifier must reject and legitimate claims it must keep, each with its verdict decided before any model saw it.

Agreement with the incumbentAnswer key written first
What it measuresSubstitutabilityCorrectness
Ground truth isThe incumbent's recorded verdictA verdict written before any model ran
A challenger that disagrees isMarked wrongChecked
Can it separate two good modelsNoYes
ReportsOne numberTwo rates, caught and kept
CostsNothing, reuses stored verdictsEvery claim labelled by hand

The last two rows are the ones that decided it. Missing a fabrication is dangerous and rejecting a good finding is merely expensive, so collapsing both into a single score hides which mistake a model is actually making. And the answer key does not flatter anyone: re-run today, nothing comes through it clean, the incumbent included. The small models did miss fabrications, so the original verdict was right by accident and wrong in method, and the model that agreed with the incumbent most often was not the one that caught the most fabrications.

The first method was itself the failure this project exists to catch: a confident, plausible, unsupported conclusion, arrived at by a human rather than a model. It held two errors, not one: it measured sameness instead of correctness, and I never checked the chance baseline that would have shown the agreement I saw was barely above guessing. The incumbent stays anyway, slower but safe: a verifier that lets even one fabrication through has failed at the one thing it is for, and its latency is paid once per case, not per event, so here correctness is the cheap thing to buy.

Whether that second pass earns its cost is itself still open, and the answer may be no. Of the claims the model-free pass accepted, the second pass rejected 12 of 225. Whether those rejections were correct is being decided by blind human labelling, the answer key held in a separate file, and the result will be published either way.

09 Limits

What these numbers do not cover

  • Detection recall is 41.7%. Measured against a corpus of 20 attacks written from ATT&CK technique descriptions rather than from the rule files, because authoring one attack per rule would score 100% by definition. No rule stayed silent on an attack it describes, so nothing is broken: the misses are techniques nobody has written a rule for yet, named individually in the project's documentation. And recall against a corpus you wrote yourself is bounded by your own imagination, so a technique I did not think of is missing from the rules and the test corpus alike. The blind spot is narrower, not closed.
  • Sample sizes are small. 64 cases, 316 claims, 49 findings that reached the second verification pass. Every rate derived from these carries a wide confidence interval, and the project reports the interval rather than the percentage alone.
  • It runs on one machine and has never seen public internet traffic. The honeypot ran on an isolated local network with a simulated attacker, and the seven-day traffic baseline that several measurements depend on has not been collected.
  • Two of the three noise-filter rules have never fired. They have never been handed input they could act on, so their real-world value is untested rather than disproven.
  • I wrote both the fabrications and the checks that catch them. The benchmark scores show the checks agree with my own idea of a fake, not an outside standard. Two catches were the exception, real and unstaged: a batch of machine-generated fakes the code caught, and a subtle claim the model rejected during a live investigation.
Run against captured honeypot traffic and synthetic endpoint telemetry, not a production estate.

10 Conclusion

What it comes down to

What the project shows

  • Structure beats prompting for trust. Strip the model's authority, no severity, no case creation, no writes, and its worst output degrades from a dangerous action into a claim the checks can catch.
  • Verification has to be independent and adversarial. Deterministic code checks the figures; a second, different model checks the reasoning, both kept blind to the investigator's own confidence.
  • Measurement is where judgment shows. The project's own worst error was a confident, unsupported conclusion, caught only by writing the answer key before the models ran.
  • Honest scope. A prototype on captured and synthetic data across 64 cases, not a production deployment. The architecture is not original either: deterministic validation of model output and mandatory evidence citation both appear in published vendor and academic work. The one property worth defending is narrower, that the first verification pass contains no model, so unlike every model-based checker it cannot itself hallucinate.

Most of the effort went into trying to prove the system did not work, and several times it did not.

The verifier was never meant to be a guarantee. All of this exists because a model will hand you a fluent, confident answer that is wrong. The most confident wrong answer on this page was not the model's, though. It was mine: small models cannot verify. I had measured whether they agreed with the model I already trusted, and never whether they were right. Writing the answers down first cost an afternoon of hand-labelling. Not doing it had already cost me a conclusion I believed.
