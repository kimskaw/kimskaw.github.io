RecipeKiosk: A Wall-Mounted Kitchen Recipe Kiosk

Turns a spare Android tablet into a dedicated kitchen display for a self-hosted Mealie recipe server. Tap an ingredient category (or several at once in Mix Mode) and get matching recipes with video, ingredients, and steps in kiosk-sized type.

Personal Android project Kotlin · Jetpack Compose · Mealie
Kotlin Jetpack Compose MVVM Room Retrofit Coil Media3 ExoPlayer Tailscale

Mealie is a solid self-hosted recipe manager, but its web UI isn't built for a flour-covered thumb tapping a screen bolted to a kitchen wall. RecipeKiosk is a purpose-built Android client for exactly that: a Samsung Galaxy A55 mounted in the kitchen, permanently on, showing category tiles instead of a browser.

It's built offline-first: the UI always reads from a local Room cache, so a dropped Tailscale link degrades to stale data instead of a blank screen.

What it does

  • Tap-to-filter categories: seven core tiles (chicken, pork, salad, vegetable, beef, fish, rice) plus a collapsed "More from Mealie" section for the rest of the tag library, ordered busiest tag first.
  • Mix Mode: tap multiple categories at once for an AND-filtered search ("chicken + ginger"), done entirely in SQL against the local cache, no network round trip.
  • Full-library search: one LIKE pass across name, description, ingredients, and tag slugs, ranked name-prefix matches first.
  • Per-recipe video: resolved in priority order: a manual override set on-device, then Mealie's own metadata, then a cached YouTube title search, with each recipe searched at most once to protect API quota.

How it's put together

The UI never talks to the network directly; it only ever reads Room. A sync writes into the cache; everything on screen comes back out of it, which is what lets a flaky Tailscale link fail gracefully instead of blanking the screen.

Challenges & what I learned

Finding

Serve the player from a real HTTPS origin

The IFrame player reached onReady then refused every video, because loadDataWithBaseURL gave the document no real origin for YouTube to verify. Fixed by serving from WebViewAssetLoader instead. A related bug wore the same disguise: the player rendered as a black sliver while reporting "cued", because under WebView's wide-viewport mode body { height: 100% } resolves to zero.

Finding

Give power users an escape hatch, but don't weaken security for it

BlueStacks, used for local verification, has no Tailscale client, so the tailnet hostname could not resolve: an environment gap, not an app bug. The fix is an optional Server IP override in Settings that swaps DNS resolution only: TLS SNI, the Host header and certificate validation all still use the real hostname, so the override routes around a DNS gap without weakening the connection.
